# 8bit Redo Postmortem

## What Went Wrong

The failed final and cute-final 8bit batches are rejected.

The core mistake was treating a visually nice multi-pose sheet as if it were a production-ready sprite sheet. Several poses were generated too close to each other, or with loose fragments near the edges. Once that happened, any automatic crop step had to guess what belonged to the pet. That guess broke important details: eyes, mouths, hands, head edges, ears, props, and left/right direction.

The deeper workflow mistake was optimizing for "many outputs quickly" instead of "one asset can survive production use." A room sprite is not finished when it looks cute once. It is finished only when the image can be scaled, mirrored, cached, placed on a red QA background, and used in both the room and mini games without losing body parts or reversing direction. The previous batch skipped that production proof.

The second mistake was mixing different asset purposes:

- Full evolution artwork can be a complete illustrated scene.
- Room and mini-game 8bit sprites must be clean, isolated production assets.
- Avatar/head assets must not be hacked out of a body sprite when a separate generated avatar is expected.

The third mistake was accepting technical checks as enough. A PNG can be `256x256`, transparent, and mirrored, while still being visually wrong. Direction, crop safety, identity, and readable face details need human-visible QA.

The fourth mistake was allowing background removal to become semantic guessing. Any method that decides "this white/dark/soft area is probably background" can destroy white mouths, eye highlights, ears, hands, or head edges. For this project, cleanup may only remove the outside transparent area or a deliberately generated flat key background that is proven not to exist inside the character.

## What Worked In The Cute Evolution Art

The cute evolution artwork worked because it was generated as a clear single-subject visual. It did not need to be split into many small moving parts. The character had enough canvas space, the composition was readable, and there was no pressure for the script to guess between neighboring poses.

For the 8bit redo, we borrow that lesson: one clear subject, enough margin, no neighboring pose contamination.

That means the 8bit production prompt should behave more like the successful cute-evolution prompt:

- one character only
- one intended pose only
- simple canvas, no scenery
- enough negative space around the whole body
- no adjacent poses
- no useful detail touching the canvas edge
- no generated checkerboard pretending to be transparency

## New Rules

1. Do not overwrite `assets/8bit/final` or `assets/8bit/cute-final` during generation.
2. Save all new work under `tmp/8bit-redo-20260827/` first.
3. Generate each pet route as isolated pose assets, not a crowded mixed sheet.
4. Do not use multi-action sheets for this redo unless the user explicitly approves that specific sheet layout after seeing a spacing test.
5. Every generated image must request a genuinely transparent background.
6. Cutting is only allowed to crop the outer transparent bounding box and fit the whole sprite into the target canvas.
7. The cutter must not infer background, erase internal alpha, fill holes, remove white pixels, or rebuild masks.
8. Head/avatar images are not generated by body-cropping unless the user explicitly asks for that.
9. Left-facing actions should be generated or mirrored from an approved right-facing action only after visual direction checks.
10. Red-background QA is mandatory before any installation into the game.
11. Every installed action must have an immediate before/after QA image kept in `tmp/8bit-redo-20260827/qa/`.
12. If any single action fails direction, crop, transparency, or identity, only that action is repaired; no broad replacement happens without a fresh route checklist.

## Transparent Output Finding

Built-in Imagen can output real alpha for simple transparent icons, but several
Hydroblob reference-based 8bit sprite attempts produced RGB images with a
painted checkerboard instead of true transparency.

That means the redo workflow needs a guarded fallback before any batch run:

- first try true transparent single-action generation
- if the saved file is RGB or has no usable alpha, reject it as fake transparent
- use a single-action solid key-color prompt instead
- choose a key color that does not appear in that pet
- convert only the configured key color to alpha
- show red-background QA before accepting

This fallback is not the previous broken cutout method. It does not use shape
guessing, body segmentation, white-pixel deletion, or component cleanup. It is
only a controlled conversion of a deliberately chosen background color.

## Required 8bit Actions

For each required route:

- stand / idle
- run right
- jump right
- crouch right
- lie right

Left versions are derived only after the right version is visually accepted:

- idle left
- run left
- jump left
- crouch left
- lie left

For flying or floating pets, the required action names still map into these game folders, but the visual semantics change:

- run right becomes hover/glide right
- jump right becomes upward or aerial movement right
- crouch right becomes lowered-hover/down pose
- lie right stays a rest pose if visually natural; otherwise it must be reviewed before use

## QA Gates

Before install:

- red background contact sheet for every pose
- no chopped head, ears, hands, eyes, mouth, props, or tail
- no neighboring-pose fragments
- internal whites and eye highlights remain opaque
- run right faces/moves screen-right
- mirrored left faces/moves screen-left
- jump/crouch/lie direction pairs are consistent
- sprite fits inside `256x256` with usable margin
- long pets such as Hydroblob, Ender Dragon, Frost Fang, and Charizard must keep full body visible

No deploy until the red QA passes.
